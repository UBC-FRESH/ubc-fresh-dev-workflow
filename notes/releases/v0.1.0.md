## What this release contains

The workflow seed, built with its own process. Phases P0 to P3 are complete and merged into `main` at `fa94b69`.

- **P0, bootstrap scaffold** (#1, PR #17, merge `2943d83`). The phase, task, and subtask roadmap, mirrored into GitHub issues. The Sphinx docs site, which is the RTFM surface. The validator `scripts/check_workflow.py`. The green dashboard `scripts/dashboard.py`. The seed generator `scripts/new_project.py`. Strict typing and numpy docstrings, a branch-coverage gate, and the embedded agent capabilities page.
- **P1, dogfood and validation** (#9, PR #28, merge `8f063fb`). A synthetic project rendered from the seed, and a fresh-clone rehearsal of `pre-commit` and the dashboard. The validator's walk mode reads the root `.gitignore`. The branch-coverage gate for `scripts/` is 95 percent. Findings F3, F4, F7, and F9 were filed as issues and resolved or deferred (see below).
- **P2, dev server kit** (#10, PR #33, merge `f998cd8`). `server/host-check.sh`, a read-only host check. `server/provision-base.sh --dry-run` and `server/new-project-container.sh --dry-run` print the dev server guide's commands and run none of them. The CI `quality` job runs shellcheck on `server/`. CI runs on the pinned runner `ubuntu-24.04`, and its actions declare Node 24.
- **P3, lifecycle playbooks and deployment** (#11, PR #38, merge `fa94b69`). The six lifecycle stages, with entry criteria, exit criteria, and a gate owner for each (`docs/reference/lifecycle.rst`). ADR 0009 keeps Phase 0 local, and repository creation moves into activation. The seed's roadmap template gives each phase an acceptance criteria block. The release and deployment guide (`docs/guides/release.rst`) marks each tag, release, and Pages step as approval-only, and its dry run used the P1 demo. The data management guide (`docs/guides/data-management.rst`). The agent roles and model routing page (`docs/agents/roles-and-models.rst`).

## Known gaps

These gaps were recorded in the phase close-out reports as stated limits, not as deviations.

- No playbook has run against a live repository, PyPI, or Zenodo. The release dry run checked commands against the installed tools (P3).
- No script has run on a lab host. The `--apply` paths are tested with stubbed `lxc`, `snap`, and `id` commands (P2).
- The port check in `server/new-project-container.sh` reads only the proxy devices that LXD knows about. It cannot see a port that other software on the host uses (P2).
- The tests do not check the wording of the plan's comment lines (P2).
- The dashboard does not run shellcheck. The check runs only in the CI `quality` job, because shellcheck is not in the dev requirements (P2, F7 below).
- The P1 rehearsal had no GitHub repository, so the GitHub steps of the close-out were not rehearsed. P4.2 and P4.3 rehearse them with approval (P1).
- The second row of the model log names the model that ran the P3 session. Its evidence is gate results, not a comparison. The maintainer confirms that row (P3).
- The seed does not ship the lifecycle, release, data, or roles pages, so a generated project has no playbooks yet (P3).
